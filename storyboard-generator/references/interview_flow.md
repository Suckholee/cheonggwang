# 인터뷰 플로우 상세 가이드

이 문서는 SKILL.md의 단계 0~4를 진행할 때 참고할 구체적 질문 스크립트, 폴백, 안티패턴을 모은 것이다.

---

## 단계 0 — 프로젝트 컨텍스트

### 추천 질문 (AskUserQuestion 4문항)

```
Q1. 프로젝트(서비스) 이름과 한 줄 설명?
    → 평문 free-form

Q2. 타깃 플랫폼?
    A. 모바일 앱 (iOS/Android)
    B. 반응형 웹
    C. 데스크톱 웹
    D. 모바일 + 웹

Q3. 이 스토리보드의 주된 용도?
    A. 개발 착수 (개발 발주/핸드오프)
    B. 디자이너 핸드오프
    C. 클라이언트 보고/검수
    D. 내부 검토

Q4. 작성자/팀과 버전?
    → 평문, "이름 / 팀 / v0.1" 형태
```

### 답을 받은 뒤

요약을 1~2문장으로 다시 보여주고 단계 1로 넘어가라:

> "정리하면, **모바일 앱 '월렛지기' v0.1** 을 **개발 착수용 스토리보드**로 작성한다고 이해했어요. 작성자는 OOO. 다음 단계로 IA(메뉴 구조) 카테고리부터 잡을게요."

---

## 단계 1 — IA 카테고리 정의 (색상 분류)

### 컨텍스트별 추천 카테고리 후보

먼저 후보를 던져라. 빈 종이 주면 사용자가 막힌다.

**B2C 앱 (일반)**
```
- 진입/계정     #F59E0B (주황) — 스플래시·튜토리얼·로그인·회원가입
- 메인          #FACC15 (노랑) — 핵심 기능 허브, 홈
- 부가기능      #9CA3AF (회색) — 알림·즐겨찾기·검색 결과
- 설정·관리     #94A3B8 (연회색) — 마이페이지·설정·고객센터
```

**B2B SaaS**
```
- 인증          #6366F1 (인디고)
- 워크스페이스  #2563EB (블루) — 대시보드·리스트·상세
- 콘텐츠 관리   #14B8A6 (틸)
- 권한·설정     #94A3B8
```

**어드민**
```
- 인증·세션     #DC2626 (레드)
- 대시보드      #2563EB
- 사용자 관리   #14B8A6
- 콘텐츠/감사   #9CA3AF
```

### 사용자가 직접 정의하고 싶다 할 때

> "원하는 카테고리 이름 + 색상(HEX 또는 색 이름) 알려주세요. 예: 〔결제 영역 #2563EB〕, 〔주문 흐름 #F97316〕"

색 이름만 알려주면 가까운 표준 HEX로 매핑한 뒤 보여주고 확인.

## 단계 2 — IA 박스 트리

### 박스 후보를 먼저 던져라

```
[진입/계정]
  B01 스플래시
  B02 튜토리얼/온보딩
  B03 로그인 (이메일/소셜/핀)
  B03a 비밀번호 찾기
  B03b 회원가입 (정보 입력 + 이메일 인증)

[메인]
  B05 홈/메인
  B06 핵심 기능 상세

[부가기능]
  B07 검색
  B08 알림센터
  B09 즐겨찾기

[설정·관리]
  B20 더보기/설정
  B21 내 정보
  B22 인증수단 관리
  B23 고객센터
```

### 박스 ID 규칙

- `B<NN>_<짧은 이름>` (예: `B05_홈메인`)
- 분기는 알파벳 suffix: `B03a_비번찾기`, `B03b_회원가입`
- 모달 / 팝업은 `M01_*` (필요 시)
- 박스가 7개 넘으면 **카테고리별 회차**로 나눠 진행

### 박스 내부 항목 인터뷰

각 박스에 들어갈 항목을 묻는다. 너무 추상적이면 막히므로 **카테고리 + 사용자 컨텍스트로 추정 후 제시 → 다듬기** 패턴이 효율적이다.

```
"B05 홈메인 안에 들어갈 메뉴들을 정리해볼게요. 보통 월렛 앱이면:
  1. 알림
  2. 사용 내역 (지갑 QR코드 같은 거)
  3. 보내기 (이체)
  4. 입출금 내역
  5. 운동 정보
  6. 소식
  7. 스토어
이 정도가 들어갈 텐데요. 빠진 것 / 빼야 할 것 / 분기되는 것 알려주세요."
```

사용자가 "보내기 안에 QR 검색, 회원 검색이요"라고 하면 즉시 정형화:

```json
{"no": 3, "label": "보내기", "subitems": [
  "보안비밀번호 등록",
  "이체정보입력 — QR코드 검색 / 회원 검색",
  "이체완료/확인"
]}
```

### 미해결 이슈 캐치

박스 인터뷰 도중 사용자가 머뭇거리거나 "이건 아직 정해져야 해요"라고 말하면 **즉시** `open_questions`에 적어둬라. 산출물에 빨간 메모로 표시된다.

> "그 부분은 'MVP 때 스토어가 없다면 스토어 대신 마이너 관리 페이지를 위치?' 라고 메모로 박아두고, 나중에 결정되면 수정하면 어떨까요?"

## 단계 3 — 박스 간 흐름(화살표)

박스 정의가 어느 정도 끝나면 화살표를 그린다. 한꺼번에 다 묻지 말고 **메인 흐름부터** 잡고, **분기/예외**는 그다음.

```
"메인 흐름: 스플래시 → 튜토리얼 → 로그인 → 홈메인 — 이대로 맞나요?
 그리고 로그인에서 분기되는 흐름이 있죠 — 비번 찾기 / 회원가입.
 회원가입 끝나면 핀번호 등록을 거쳐서 다시 로그인으로 돌아오는지, 바로 홈메인으로 가는지?"
```

label이 필요한 화살표(예: "비밀번호 분실 시")는 명시하고, 명시 안 해도 자명한 화살표는 비워둔다.

## 단계 4 — 화면별 상세 페이지

### 어떤 화면을 상세 페이지로 만들지

모든 박스에 만들 필요는 없다. **개발 착수에 직접 영향을 주는** 화면 위주로 5~15장. 사용자가 잘 모르면 가이드:

> "보통 개발자가 보고 바로 구현 들어갈 수 있는 수준의 화면을 골라요.
> 핵심: 로그인 / 회원가입 / 메인 / 핵심 액션 (이체·결제·작성) / 상세
> 선택: 검색 / 설정 / 빈 상태 화면
> 어떤 화면들로 갈까요?"

### 한 화면 인터뷰 — 표준 시퀀스

화면 하나를 인터뷰할 때는 다음 6단계 순서대로 한 단계씩:

#### (1) PATH 확인
```
"이 화면의 PATH 한 줄 적어주세요. 예: '회원가입 > 정보 입력 > 이메일 인증'.
 보통 IA 트리에서 부모를 따라가면 자동으로 잡혀서 제가 추정해서 보여드릴게요. 맞나요?"
```

#### (2) 메인 목업 이미지 업로드
```
"이 화면의 디자인 시안이 있으시면 이미지 파일을 업로드해주세요. (jpg/png/svg 모두 OK)
 시안이 아직 없으면 SVG로 단순 와이어프레임 자동 생성해 자리만 잡아둘 수 있어요."
```

업로드된 이미지는 그대로 화면 상세 슬라이드의 중앙에 박힌다.

#### (3) 번호 어노테이션 (입력 필드)
```
"이 화면에서 사용자가 '입력하는' 영역들을 위에서부터 번호 매겨볼게요.
 예: ① 이메일, ② 비밀번호. 이 화면에는 어떤 입력 필드들이 있나요?"
```

각 필드별로 **Function Description**:
- 입력 제한 (글자수, 형식)
- 허용 문자 (영문/숫자/특수문자)
- 유효성 체크 시점·기준
- 비밀번호 표시 토글 같은 부가 동작

#### (4) 알파벳 어노테이션 (버튼·링크)
```
"이번엔 사용자가 '누르는' 영역들을 알파벳으로 매겨볼게요.
 Ⓐ 로그인 버튼, Ⓑ 비밀번호 찾기 링크, Ⓒ 회원가입 버튼처럼요."
```

각 버튼/링크별 **Button Description**:
- 활성화 조건 (입력값 유효 시 등)
- 클릭 시 동작 (이동할 화면 / API 호출 / 모달)
- 실패 시 처리

#### (5) 컴포넌트 상태 변형 스택 (좌측)
```
"이 화면 좌측에 컴포넌트 상태 변형을 세로로 쌓을 거예요. 표준 프리셋:
  - 기본 상태
  - 포커스 인 (커서 들어왔을 때)
  - 입력 시 (글자 입력 중)
  - 입력값 숨김 시 (비밀번호 마스킹)
  - 포커스 아웃 - Valid (검증 통과)
  - 포커스 아웃 - Invalid (검증 실패)
이 중에 보여줄 것들을 골라주세요. 추가로 보여줘야 할 상태가 있으면 알려주세요."
```

상태 프리셋의 정확한 정의는 `component_states.md` 참고. 보통 입력박스 화면에 6개, 단순 버튼 화면에 3개 정도면 충분.

#### (6) Validation 메시지 표 (우하)
```
"검증 실패 / 시스템 에러 / 안내 메시지를 표로 정리할게요.
 컬럼은: 체크 시점 / 조건 / 메시지 / 노출 유형 (인풋박스 하단 문구 / 디자인 팝업 / 토스트 등).
 떠오르는 케이스부터 알려주세요. 빠지기 쉬운 거: 계정 잠금, 기기 변경, 네트워크 오류, 권한 거부."
```

### 화면별 마무리

한 화면 인터뷰가 끝나면 **요약 카드 보여주고 확인**:

```markdown
## 화면 상세: 로그인 페이지 (요약)
PATH: 진입 > 로그인
메인 목업: login_screen.png ✓ 업로드됨
번호 ①②: 이메일 / 비밀번호 (각 Function Description 채움)
알파벳 ⒶⒷⒸ: [로그인] / 비번찾기 링크 / [회원가입]
상태 변형: 기본 · 포커스 인 · 입력 중 · 마스킹 · Valid · Invalid (6개)
Validation 표: 4행 (이메일 형식 오류 / 비번 불일치 / 계정 잠금 / 기기 변경)

이대로 갈까요?
```

확인 받기 전엔 다음 화면 넘어가지 말 것.

## 안티패턴 (하지 말 것)

1. ❌ **"화면 12장에 대해 모든 항목을 한꺼번에 알려주세요"** 식 거대 폼.
2. ❌ 사용자의 말 그대로만 적기 — 정형화하지 않으면 PPT 슬라이드가 모호해진다.
3. ❌ 추정으로 채운 부분을 표시 없이 묻어버리기.
4. ❌ 디자인 시안 강요 — 시안 없어도 fallback으로 진행하고, "시안 나오면 자리에 끼워 넣을 수 있어요" 안내.
5. ❌ Function Description / Button Description 을 한꺼번에 묻기 — 차라리 번호별·알파벳별로 1개씩 차근차근.
6. ❌ Validation 표를 빈 칸으로 두기 — 최소 "이메일/비번 형식 오류 + 계정 잠금" 두 행이라도 채워라.

## 폴백 — 사용자가 막막해할 때

> "막막하면 제가 일반적인 [도메인] 스토리보드 1차 초안을 자동으로 만들어볼게요.
> auto_filled 표시로 빨간펜 봐주시기 좋게 만들 거고, 빈 곳은 open_question 빨간 메모로 박아둘게요."

→ 이 경우 **모든 자동 채움 항목에 `auto_filled: true`** 마크업 필수. 산출물에서 즉시 식별 가능해야 함.
